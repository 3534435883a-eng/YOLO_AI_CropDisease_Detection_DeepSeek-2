# 仿真审计

打真实 HTTP 接口跑评测批次，逐条核对项目**自己声明的性质**，并列出无法从仿真中核实的数据缺口。

```bash
# 前置：MySQL 在跑，后端在跑（见 docs/tomato-greenhouse-agent.md 部署顺序）
python tools/eval-audit/run_simulation_audit.py --base http://localhost:9999 --days 120 --seed 20260921
```

脚本只读：只调 `/eval/runs` 与 `/eval/{id}/matrix`，不改数据库、不改代码。

**为什么要有它**：项目把"同基线、同种子、同模型版本 ⇒ 逐值一致"写成了卖点。这类性质必须能被反复验证，
否则只是一句话。此前只有单元测试在断言它，而单元测试跑在测试进程里；本脚本验证的是**部署后的服务**。

## 2026-09-26 审计结果（120 天，seed=20260921，7 档）

| 核对项 | 结果 |
|---|---|
| 同种子重跑逐值一致 | ✅ 7 档 × 20 个数值字段全部相同 |
| 换种子确实改变结果 | ✅ 出现 108 处差异（`seed` 不是装饰参数） |
| 控制器状态不跨档污染 | ✅ 规则档在同种子两次运行间完全一致 |
| 设备互斥硬约束 | ✅ 7 档 `constraintViolations` 全为 0 |
| P→PI→PID 消融方向 | ✅ 超温 0.677 → 0.517 → 0.500，与"积分消偏、微分抑超调"一致 |

**可复算性额外加强验证**：同一批次分别在「JIT 热运行」与「`-Xint` 纯解释模式」下执行
（后者耗时 84.3 秒 vs 3.6 秒），`P2_RULE_ENGINE` 的精确存储值均为 `0.7765`，
`diseasePressureIntegral`、`wFruit` 等亦逐位相同。**解释执行与 JIT 编译不产生浮点差异**，
这条卖点比原先的验证更硬。

## 一处虚惊（记录教训）

审计过程中曾误判"测试进程给 0.777、部署进程给 0.776"，怀疑破坏可复算性。实际是
**Java 的 `String.format("%.3f")` 与 Python 的 `%.3f` 对同一个 double `0.7765` 的格式化差异**：
Java 按 HALF_UP 进位到 `0.777`，而该 double 的二进制值略小于十进制 `0.7765`，Python 下舍到 `0.776`。

**教训：跨语言比对数字必须比精确值（JSON 原值），不能比 `printf` 输出。**

## 数据缺口与缺陷（审计实际看到的）

### 一、口径不一致：灌溉水费按 10 倍计 —— **已于 2026-09-26 修正**

| 位置 | 原值 | 含义 |
|---|---|---|
| `TomatoSimulationEngine:19` | `IRRIGATION_L_PER_TICK = 60.0` | **物理**：60 L 抬升基质含水率 |
| `TomatoDecisionPolicy:58` | `"WATER", "60.000"` | 规则层声明的滴灌水量 |
| `ResourceRates:41` | `IRRIGATION_M3_PER_STEP = 0.6` | **记账**：按 600 L 计费 |

物理上浇 60 L，成本里算 600 L（实测 P2 档 120 天用水 804.00 m³ = 1340 步 × 0.6 m³，
确认走的是记账侧）。四处口径中三处为 60 L，判定记账侧是错误。

**已修正为 `0.06 m³`**，并新增 `ResourceAccountingTest` 锁住物理侧、记账侧、规则层声明的等式
（`IRRIGATION_L_PER_TICK` 因此改为 public，以便测试直接引用）。

**后果比"报表列错"严重得多**：

| 档位 | 水耗 m³ | 成本元 | 利润元 |
|---|---|---|---|
| P2 规则引擎 | 804.00 → 80.40 | 8052.8 → 5520.2 | −862.4 → **+1670.2** |
| P3 智能体 | 768.60 → 77.10 → **73.44** | 8994.2 → 6574.5 → **6548.1** | +3905.8 → +6340.0 → **+3914.3** |
| P4 仅 P | 804.00 → 80.40 | 8105.8 → 5573.2 | −1379.3 → **+1153.3** |
| P5 P+I | 781.80 → 78.18 | 9696.6 → 7233.9 | −1642.0 → **+820.6** |
| P6 PID | 781.80 → 78.18 | 9639.2 → 7176.5 | −1607.6 → **+855.0** |

- "规则档亏损、只有智能体档盈利"这个叙事**本身是记账错误的产物**：修正后 7 档中 5 档盈利。
- `P3_AGENT` 的候选前瞻用 `resourceCostYuan` 打分，**水价虚高 10 倍一直在扭曲智能体的灌溉决策**：
  修正后其果实干重由 452.41 变为 452.92，用水随之上升。
  随后「土壤水分口径修正」又把它移到 361.17（见 docs/eval/README.md 该节）——
  两次修正合起来说明：P3 早先的优势里有一部分来自能在两套物理之间错位。
- 此前引用过这些数值的材料需要重算。

### 一之二、土壤水分存在两份互不相同的状态 —— **已于 2026-09-26 修正**

与上条同属"口径不一致"，但后果更重：**同一个物理量被实现了两次**。

| 档位 | `SoilState.soilMoisturePct`（原**作物**读） | 引擎 `SimulationState.soilMoisturePct`（**策略**读） |
|---|---|---|
| P0 无灌溉 | 53.59 ~ 62.00 | **5.00 ~ 61.98** |
| P2 规则档 | 61.37 ~ 75.00 | 44.98 ~ 61.98 |

同样气象、同样 120 天，**最大相差 49 个百分点**。规则层按引擎那份灌溉，作物按 `SoilState` 那份生长，
而后者从不跌破 53.6% → **作物在任何档都不受水分胁迫**（`waterFactor` 全季恒为 1.000），
**灌溉对产量零影响、只影响成本**。修复前"完全不灌溉"的 P0（80.86）几乎追平"有灌溉"的 P1（82.28）就是这个症状。

两处不一致都在 `PerformanceEvaluationService`：主循环的 `coupled` 与 `P3` 用来择优的 `project()`。
第二处尤其严重——**P3 在"永不缺水"的世界里择优、被评分在"会缺水"的世界里**，
实测干重一度从 452.92 崩到 96.47、用水从 77.10 掉到 21.24 m³，看起来像"AI 不如规则"。
两处统一取引擎那份后：P0 的 `waterFactor` 降到 0.300（真受胁迫），
`P3` 回到 361.17（仍优于规则 257.72，但**优势由 +76% 降为 +40%**）。

**该修让结论变小、但更可信**：原先 P3 的一部分优势来自能在两套物理之间错位。详见 `docs/eval/README.md`。

**土壤模型自身系数（2026-09-26 第二批，已修）**：
ET0 缺 FAO-56 的日序天文辐射 `Ra`（**小约 50 倍**，实算 0.065 mm/day vs 正常 3–6）；
`MM_TO_PCT_VOL = 1.6` 按 0.25 m 根深应为 **0.4**（差 4 倍）；
灌溉量按其注释与引擎对齐为**每次事件 0.42 mm**（原 `IRRIGATION_MM_PER_STEP = 1.2` 名字说"每步"、
注释说"mm/day"，**自相矛盾**，已改名并删旧常量）。新增 `LATITUDE_DEGREES = 30.7`（成都）
与 `DAILY_TEMPERATURE_RANGE_C = 12.0`（刻意与引擎室外模型振幅一致），两者均已进参数出处登记。

修后实测：累计灌溉 **16.75 → 563.03 mm**（落进番茄需水 240–600 mm）、
EC **不再触底**（1.150→0.300 锁死 → 1.158~1.201 平衡）、pH 由几乎不动变为 **6.200~7.313**、
累计淋洗氮 0.3 → 18.4 kg/ha。**评测矩阵未变**（作物读的是引擎那份水分）。

**仍待决：氮收支配平。** 探针现在直接打出这笔账（用已有量算清、不猜）：

```
初始 90.0 + 施肥 26.8 − 淋洗 18.4 − 期末 0.0 = 作物带走 98.4 kg/ha
施肥投入占带走量的 27.2%
```

投入不足带走量的三成 → 速效氮第 20 天见底、养分因子此后长期钳在 `0.3` 下限 →
**土壤/养分子系统目前对产量没有任何影响**。不当场配平的原因：模型把"当步新增干物质"近似为
`wTotal × 2%/天`（代码注释已声明是刻意简化），该近似在生物量大时给出过高日需求，需求被前load；
而 `NUTRIENT_LOW/HIGH = 20/90` 又把初始值顶在"充足"边界。**定值需要一份可引用的番茄氮收支**
（每吨果实带走多少 N、各生育期吸收比例），靠现有三个未标定系数互调只会把一处错误换成另一处。

### 二、拒答能力被离题负样本严重高估 —— 已量化，未修

`RetrievalEvalTest` 原有 10 条负样本里 9 条完全离题（写诗、足球、量子计算、手机电池…），
拒答它们几乎不费力气。新增 18 条**难负样本**（农业外表但库中确实无依据，标签逐条核验自
`docs/vision-class-kb-mapping.md` §四 与 `developer_holdout.jsonl`）后：

| 负样本组 | 题数 | 拒答准确率 |
|---|---|---|
| 离题负样本 | 10 | **100.0%** |
| 难负样本 | 18 | **27.8%** |

**落差 72 个百分点。** 机理已定位：多条漏判样本的 IDF 加权覆盖率仅 0.06–0.22（阈值 0.45），
本应判低分，却被 `isLowScore` 的 `evidenceCoOccurs` 分支救下——只要某切块同时含"作物名 + 防治"
这类通用词就满足"证据共现"，**即使主题词在语料中根本不存在**。该判据无法区分
"命中主题"与"只命中通用词"。修判据需先定拦截规则，不宜按逐题结果调参。

### 三、湿帘用水在评测平台未折算

数字孪生侧有 `TomatoSimulationEngine.coolingPadEvaporationLiters(...)` 按进风温湿差动态计算，
评测平台侧完全不计。PID 档比规则档更常用湿帘，因此**其水耗被低估**，跨档水耗比较对这一项不公平。

### 四、人工对照档是稻草人

`P1_FIXED_MANUAL` 利润 −2724.5，**比不干预的 P0_NONE（−1635.3）更差**，产量仅高 1.7%（748 vs 735 kg）。
定时灌溉花了水钱却不增产。它更像"花钱不办事"的对照，而非"凭经验管理的农户"的合理代表，
作为"AI 优于人工"的论据说服力很弱。若要用于对外材料，需重设为合理的经验管理策略。

### 五、评测结果不落库，重启即失

`EvaluationController` 的批次只缓存在内存（`MAX_CACHED_BATCHES=5`），JVM 重启后
`/eval/{batchId}/matrix` 直接报 `EVAL_BATCH_NOT_FOUND`。**"跑一次、反复看"在重启后失效**，
且评测数字无法作为可追溯证据留存。对比之下会话历史已做持久化，评测侧仍是缺口。

### 六、无区分度的指标

`fruitSetRate` 在全部 7 档恒为 `1.000`，不提供任何信息（可能模型内该量不衰减）。
放在矩阵里会误导读者以为"坐果率表现完美"。

### 七、需要外部数据才能补的缺口

- **无现场实测**：缺 7–14 天以上带时间戳的棚内外温湿度、CO₂、PPFD、基质含水率、阀/窗/风机状态与水电累计量
  → **无法声称预测精度**，无法计算 MAE / 偏差 / 极端天气误差 / 参数敏感性。
- **参数未校准**：换热系数 0.12 / 空气水汽交换 0.09 / 侧窗 0.35 / 屋窗 0.15 / 排风 0.35、
  湿帘效率取假设的 80%、滴灌 60 L/次、各设备能耗与 CO₂ 定额——全部是演示参数。

  **现已可查询**（2026-09-26 接入）：`GET /ai/agent/parameters/summary` 给出缺口统计，
  `POST /ai/agent/parameters/refresh` 按当前源码重建登记。版本 `sim-params-2026-09-26` 共 108 条，
  **带出处 URL 的只有 1 条**（FAO-56 湿度计常数 γ），83 条"文献区间待核对"、24 条"示例值需换当地数据"。
  详见 `docs/tomato-greenhouse-agent.md` 的「参数出处登记」。
- **视觉侧未校准**：YOLO 标签与置信度未标定（`docs/vision-class-kb-mapping.md` §五 已记录零宽空格与错译标签），
  视觉记录固定 `PENDING_REVIEW`；知识库覆盖 25/50，`tomato/Mosaic_V` 等坚持不映射。
- **回答质量轴无人工评分**：`tools/answer-eval-kit` 已备好抓取与评分工具链，但尚未产生任何标注数据。

## 引用这些数字时的最低要求

- 只能表述为**场景推演与同模型内的基线对比**，不得表述为经过现场验证的预测系统。
- 水耗/成本/利润三列已于 2026-09-26 按修正口径重算（见缺口一）。**引用 2026-09-26 之前的数字需重算。**
- **报拒答能力时必须同时给出难负样本的数字**（100% vs 27.8%，见缺口二）。
  只报"离题负样本拒答 100%"会严重高估系统能力。
- 报"AI 档更强"时必须同时给出代价：`P3_AGENT` 高温暴露 43155 min 比规则档 29490 min **高 46%**，
  是用热风险换来的产量（3283.4 vs 2342.9 kg）；`P5/P6` 耗电约为规则档的 2.4 倍。
- 湿帘用水未折算（缺口三），涉及湿帘用量的水耗对比不宜对外引用。
