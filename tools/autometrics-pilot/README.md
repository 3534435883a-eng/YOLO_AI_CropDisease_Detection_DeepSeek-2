# AutoMetrics 试点：视觉类别 → 知识库条目 映射判定

**状态：阶段一完成（数据集 + 基线）。阶段二（运行 AutoMetrics 本体）结论是"不该跑"，见文末。**

## 这个试点要回答什么

评估 `docs/vision-class-kb-mapping.md` 里那个**人工逐条裁定**的任务能否被自动判据复现：
给定一个视觉模型类别标签和一个候选知识库条目，判断两者是否指同一种病害/虫害。

选它做零标注成本试点的理由：标签来自文档中**已有的实质裁定**（不需新增专家标注），
但**字面匹配无法复现**——文档记录的失败模式正是"子串出现在原文里"就判为对应。
因此它既是零成本的，又是非平凡的。

## 文件

| 文件 | 作用 |
|---|---|
| `build_dataset.py` | 从 `cropdisease.sql` + `curated-*.json` 读知识库，按映射文档生成数据集；**校验每个条目名真实存在，对不上即报错退出** |
| `dataset.jsonl` | 产出：31 条（25 正 / 6 负），每条带 `label_rule` 与 `label_cite` 指回文档位置 |
| `baselines.py` | 三条基线 + 手写的 Spearman / Kendall τ-b（不给项目环境加 scipy 依赖） |
| `llm_cache.json` | LLM 回答缓存，重跑不再产生费用 |

运行（用项目现有解释器即可，无需新依赖）：

```bash
python tools/autometrics-pilot/build_dataset.py
python tools/autometrics-pilot/baselines.py --baseline literal
DASHSCOPE_API_KEY=... python tools/autometrics-pilot/baselines.py --baseline llm --model qwen-turbo
```

## 结果（31 条，25 正 / 6 负）

| 基线 | 准确率 | 平衡准确率 | Kendall τ-b |
|---|---|---|---|
| A1 字面匹配（仅比条目名） | 80.6% | 75.3% | 0.457 |
| A2 字面匹配（词干 × 全文，**文档记载的首版方法**） | 74.2% | **46.0%** | **−0.129** |
| B 单条 LLM 判据（neutral 提示，**诚实基线**） | 93.5% | 83.3% | 0.679 |
| B′ 单条 LLM 判据（hinted 提示，泄题） | 100% | 100% | 0.900 |

**A2 如实复现了文档记载的失效模式**：正例召回 23/25，但**负例召回 0/6**——它把每一条负例都判成对应。
平衡准确率 46.0%（低于随机）、τ 为负，说明该判据在"不该映射"这一侧没有任何区分力。
这与文档 §一 的结论一致，也说明本数据集确实有区分度。

四条 §三 被否决的候选（`neg-001`–`neg-004`）在 A2 上全部误判为对应，与文档给出的否决理由
（反向证据「不同于…枯萎病」、巧合同串「地面枯卷叶」「紫褐斑」）逐条吻合。

**判别核心是 `neg-005`/`neg-006`**：中文标签与条目名**完全相同**（`Scald(纹枯病)` vs 水稻纹枯病、
`Downey_Mildew(白粉病)` vs 葡萄白粉病），但英文标签揭示中文标注是错译，正确答案是"不对应"。
纯字面方法必然答错；neutral 提示下 qwen-turbo 也**恰好只错这两条**。

## 为什么阶段二不该跑

1. **样本量不足以区分方法。** 诚实基线只错 2 条，而负例总共只有 6 条。
   即使 AutoMetrics 把这两条都改对，也是在 6 个负例上移动 2 个样本——**这个差异在统计上不可解释**。
   论文的设计点是"不到 100 条标注"，且需要划分拟合集与测试集来学习指标权重；
   31 条再切分就没有测试集了。
2. **任务对单条判据已经太容易。** 诚实基线 τ-b 已达 0.679，天花板效应使"多指标融合是否更好"无从检验。
   论文声称的 +33.4% 需要基线本身有较大缺口才有观测空间。
3. **判据提示词会泄题，且已实测。** 第一次运行的提示词里写了"名称相同不代表同一种、名称不同也可能指同一种"，
   等于把本数据集上唯一的判别线索交给模型，得到 100% 准确率。
   该结果**不是基线**，脚本里保留它只作上限对照，且已在输出中标注"泄题，非基线"。
   这条教训本身值得记录：**基线跑出满分时，先怀疑提示词，不要先相信结论。**

## 如果要继续，三条路

- **（推荐）转做回答轴。** 项目最弱的一轴是"回答质量"——`docs/eval/README.md` 自己承认现有指标只是
  "引用编号有效率"，且"不能证明文字在语义上被证据充分支持"。AutoMetrics 的正当用途在这里，
  但前提是拿到约 50–80 条农技人员对回答的评分。这是人力投入，不是编码任务。
- **扩充本数据集到约 100 条。** 需要人工再裁定约 70 对候选，且 §四"无任何线索"的 22 类
  **不能**直接用检索候选凑负例：文档明说其中存在"疑似对应但未获证据"（如 `小麦 Loose_Smut(松秕病)`
  与知识库"小麦散黑穗病"），把它们标成负例会**制造假标签**。
- **仅做工具链冒烟测试。** 在 31 条上跑通 AutoMetrics，只验证"能装上、能在本项目数据上产出报告"，
  结论明确标注为工具可用性，**不得**当作方法有效性的证据。

## 边界（必须与数字一起引用）

- 标签是**开发者逐条裁定**，文档本身声明"没有农技专家双人标注"，因此本文所有结果只能称为
  "复现开发者裁定的能力"，不是农艺准确率，也不能称独立验证。
- `dataset.jsonl` 的 31 条中，负例 6 条全部来自文档明确做出实质裁定的情形；
  §四"无任何线索"的 22 类**未纳入**（理由见上）。
- 文档 §三 标题写"5 条"但表格实际只有 4 行；本数据集按**实际表格**取 4 条，未替文档补第 5 条。
- LLM 基线把项目自有的知识库文本发往阿里云 DashScope 端点。文本为该库的农业技术参考资料与
  人工改写摘要，不含用户数据；若这不可接受，请只用 A1/A2 两条本地基线。
- 运行 A1/A2 不需要任何 API key，也不需要联网。
